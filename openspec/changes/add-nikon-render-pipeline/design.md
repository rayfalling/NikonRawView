## Context

见 `proposal.md` — Why。此处只记录影响实现方式的既有事实，均为本机实测：

- **`rawler` 0.6 能解 Z8 的 NEF**：277 ms，得到 8280×5520 的 CFA（RGGB，16 bps），裁切区 8256×5504 @(12,8)，白电平 15892，黑电平 1008
- 该结果与 LibRaw 0.22.1 的结论**交叉验证一致**：白平衡 `[1.8125, 1.0, 1.5703]` 对 `[1.812, 1.0, 1.57]`
- `rawler` 直接提供 **A 与 D65 两个光源下的相机色彩矩阵**，正是色彩管线所需
- NX Studio 的 `PicCon.bin` / `PicCon21.bin` 是**携带配方记录的模板 TIFF**（标签体系与 NP3 同源、标量编码同为 `[值][0x04]`），但**不含 257 级曲线**——已用「257 个 u16 单调递增」扫描确认。故基准变换仍须拟合
- NX Studio 导出的 TIFF 内嵌 ICC 为 `Nikon sRGB 4.0.0.3002`（8,684 字节）
- 解析层已完成（`openspec/specs/`）：配方身份与配方本体都可取出

**运行约束**：沙箱内 `~/.cargo` 不可写，且 crates.io 拉取被 schannel 拦截（`SEC_E_NO_CREDENTIALS`）。引入依赖后**每次 `cargo build` 都需提权执行**。

## Goals / Non-Goals

**Goals:**

- NEF → 工作空间线性 RGB 的完整管线，中间结果可检查、可复现
- 基准配方的渲染以**尼康自身**为基准，且质量以 ΔE00 量化报告
- 管线各阶段边界清晰：解码、色彩、渲染三者可独立验证

**Non-Goals:**

- 不做浏览/选图路径。浏览的答案是抽内嵌预览（约 15 ms），属另一个变更
- 不处理 ADL。ADL 是空间性操作，需单独的提取变更
- 不做 TIFF 导出与 LrC 交付（`crs:` XMP、ICC 嵌入、A/B 模式）
- 不做 GPU 加速。本管线面向导出，CPU 足够
- 不支持 Z8 以外的机型调优。管线按通用方式实现，但不为其他机型做标定

## Decisions

### 决策一：用 `rawler` 而非 LibRaw

**理由**：纯 Rust，不需要 C 构建链；实测能解 Z8 且关键参数与 LibRaw 一致。

**备选**：LibRaw + FFI。暂缓——需 CMake + MSVC 构建 C 库并维护绑定，收益是许可更宽松与可能更好的机型覆盖。解码层在接口之后，替换是受控改动。

### 决策一·补：如实记录 `rawler` 的许可为 LGPL-2.1，并保留替换路径

**更正**：本设计的早期版本称 `rawler` 为 MIT/Apache-2.0，**该说法错误**。经查证：

- `rawler`、`rawloader`、`quickraw` 均为 **LGPL-2.1**
- `imagepipe` 为 LGPL-3.0-only
- `libraw-rs` / `libraw-sys` 为 MIT/Apache-2.0，但其绑定的 LibRaw 本体为 LGPL-2.1 / CDDL-1.0 / 商业三重许可

即：**所有纯 Rust 的 RAW 解码器都是 LGPL**。许可宽松的唯一组合是「MIT 的绑定 + CDDL 的 LibRaw 本体」。

**当前处置**：继续使用 `rawler`，但满足以下全部条件

1. 本仓库自身仍为 MIT OR Apache-2.0；`rawler` 是独立依赖，其源码不进入本仓库，本仓库不对其重新许可
2. README 与 design 明确标注：**产出的二进制链接了 LGPL-2.1 代码**，分发该二进制者需履行 LGPL-2.1 义务（随附许可证与对应源码、允许重新链接）
3. 本仓库只发布源码，不发布二进制；由源码构建本身即满足「提供对应源码」
4. 解码层位于接口之后，替换为 LibRaw(CDDL) 是受控改动而非重写

**触发重评的条件**：若要分发二进制，或把本项目整体改为更严格的许可，则改用 LibRaw + CDDL，或自行实现解码。

**备选**：自行实现尼康解码。已否决——尼康的压缩格式、双增益与 CFA 归一化工作量与风险远超其价值，且**相机色彩矩阵并不在文件里**（实测 `dng_tags` 为空），自行实现同样需要外部相机数据库。

### 决策二：接受"引入依赖"的代价，并以离线构建消除提权需求

**更正**：本设计的早期版本称"构建必须提权执行"。经实测，`cargo build --offline` 在沙箱内**无需提权即可成功**——依赖一旦进入本地缓存，构建过程完全离线。

**处置**：README 记录两条构建方式——常规 `cargo build`（需要网络）与 `cargo build --offline`（缓存已就绪时，沙箱内亦可）。后者是沙箱与离线环境下的路径。

### 决策三：去马赛克自行实现，不移植 GPL 代码

**理由**：darktable 的去马赛克为 GPL-3.0，移植会污染本仓库的许可。

**取向**：采用许可兼容（BSD/MIT/Apache）的算法与实现作为参考，来源在代码中标注。

### 决策四：管线顺序固定为「黑电平 → 白平衡 → 去马赛克 → 相机矩阵 → 工作空间 → 基准 → 配方」

**理由**：这是 dcraw / LibRaw 一脉的既定顺序，白平衡在 CFA 上做可避免先插值再缩放带来的色边。工作空间的转换必须早于基准变换——因为基准变换是在**显示参考**下拟合的，顺序颠倒会让拟合结果无法复用。

**要求**：顺序必须确定且可被查询（spec 已写成场景），不允许隐式依赖调用次序。

### 决策五：工作空间取 ProPhoto 线性

**理由**：与 Lightroom Classic / Camera Raw 的内部工作空间一致，使交付环节无需二次转换（这一点在早前的导出规格中已锁定）。

**要求**：中途不裁切色域、不截断负值，色域映射推迟到最终编码。

### 决策六：基准变换表示为「一维色调曲线 + 三维色彩查找表」

**理由**：基准渲染同时包含**非线性色调**与**色彩重映射**两部分，用单一形式表达都别扭——纯矩阵无法表达色调曲线，纯 3D LUT 无法覆盖 HDR 的无限动态范围。拆成两部分后各自可拟合、可单独诊断。

**备选**：只用 3D LUT（动态范围受限）；只用曲线 + 矩阵（色相变化拟合不了）。均已否决。

**约束**：具体规模（曲线采样数、LUT 边长）在实现中由 ΔE 结果决定，不属于 spec 层面。

### 决策七：参考导出必须先按其内嵌 ICC 转换

**理由**：实测 NX Studio 导出的 TIFF 内嵌 `Nikon sRGB 4.0.0.3002`。若当成 sRGB 处理，拟合会把 ICC 的差异吸收进基准变换，产出一个"看起来能过但整体偏色"的结果。

### 决策八：标定数据与渲染代码分离

**理由**：基准变换会随更多参考样本而改进，不应每次重编代码；且 spec 要求多份基准（NEUTRAL、FLEXIBLE COLOR）共存。

## Risks / Trade-offs

- **基准变换可能无法用「曲线 + 3D LUT」拟合到目标精度** → spec 已要求未达标时**明确报告而非静默接受**；若始终不达标，退路是改用直接的三维查找表或增加分段
- **参考导出在 Nikon sRGB 空间，色域受限** → 高饱和区域无法被标定。缓解：优先确认 NX Studio 是否能导出更宽色域的参考（Adobe RGB / ProPhoto）；不能则把标定范围限定在 sRGB 色域内并**在报告中标注该限制**
- **ADL 未关会污染标定** → 参考导出清单把"ADL 关闭"列为前提，校验不通过即排除
- **引入依赖后构建需提权** → 写入 README 与 design；若不接受，退路是回到零依赖但放弃 RAW 解码
- **去马赛克质量直接影响 ΔE** → 拟合误差与去马赛克伪像会混在一起。缓解：先用一张参考样本检查去马赛克本身，再进入拟合
- **参考样本数量少可能导致过拟合** → 拟合集与验证集分开，报告在验证集上的 ΔE

## Open Questions

- **NX Studio 能否导出更宽色域的参考？** 影响高饱和区域能否被标定。可在实现标定工具时先探测，不作为前置阻塞；若不能，按 Nikon sRGB 范围标定并标注。
- **基准变换的具体规模**（曲线采样数、LUT 边长）。可在实现中由 ΔE 与内存占用权衡决定，不改变 spec 的任何场景。
