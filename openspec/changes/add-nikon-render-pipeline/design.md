## Context

见 `proposal.md` — Why。此处只记录影响实现方式的既有事实，均为本机实测与查证：

- **LibRaw 0.22 可解 Z8 的 NEF**：`dcraw_emu` 全流程（解码 + 去马赛克 + 写 PPM）耗时 3676 ms。源码 2.9 MB，实测 `nmake /f Makefile.msvc` 可构建成功
- 白平衡与尺寸结论经两套独立实现交叉验证一致：`rawler` 0.6 给出 `[1.8125, 1.0, 1.5703]`、8280×5520、裁切区 8256×5504 @(12,8)，LibRaw 0.22.1 给出 `[1.812, 1.0, 1.57]`
- **相机色彩矩阵不出现在 NEF 里**（实测 DNG 标签为空），由解码器内置的机型标定提供。LibRaw 经 `libraw_get_rgb_cam` 暴露「相机 → 输出空间」矩阵
- NX Studio 的 `PicCon.bin` / `PicCon21.bin` 是**携带配方记录的模板 TIFF**（标签体系与 NP3 同源、标量编码同为 `[值][0x04]`），但**不含 257 级曲线**——已用「257 个 u16 单调递增」扫描确认。故基准变换仍须拟合
- NX Studio 导出的 TIFF 内嵌 ICC 为 `Nikon sRGB 4.0.0.3002`（8,684 字节）
- 解析层已完成（`openspec/specs/`）：配方身份与配方本体都可取出

**运行约束**：沙箱内 `~/.cargo` 不可写，且 crates.io 拉取被 schannel 拦截（`SEC_E_NO_CREDENTIALS`）。因此本变更**不引入任何 crate 依赖**，LibRaw 以 `build.rs` + 手写 FFI 接入；零依赖下 `cargo build --offline` 可直接工作。

## Goals / Non-Goals

**Goals:**

- NEF → 工作空间线性 RGB 的完整管线，中间结果可检查、可复现
- 基准配方的渲染以**尼康自身**为基准，且质量以 ΔE00 量化报告
- 管线各阶段边界清晰：解码、色彩、渲染三者可独立验证

**Non-Goals:**

- 不做浏览/选图路径。浏览的答案是抽内嵌预览（约 15 ms），属另一个变更
- 不处理 ADL。ADL 是空间性操作，需单独的提取变更
- 不做 TIFF 导出与 LrC 交付（`crs:` XMP、ICC 嵌入、A/B 模式）
- 不做 GPU 加速。本管线面向导出，CPU 足够
- 不支持 Z8 以外的机型调优。管线按通用方式实现，但不为其他机型做标定

## Decisions

### 决策一：用 LibRaw（CDDL-1.0），不引入任何 Rust crate

**理由**：RAW 解码依赖机型标定数据库（**相机色彩矩阵并不在文件里**，实测 DNG 标签为空），自研不现实。在可选实现中，**只有 LibRaw 的许可允许无牵绊地分发二进制**。

**备选与否决理由**：

| 备选 | 否决理由 |
|---|---|
| `rawler` / `rawloader` / `quickraw` | 均为 **LGPL-2.1**；`rawler` 还强制依赖 `tokio`(full)、`image`、`exr`，为读拜耳阵列拖入 129 个 crate |
| 自行实现尼康解码 | 工作量与风险远超其价值；且仍需外部机型标定数据库 |
| `libraw-sys` / `libraw-rs` | 实测 `libraw-sys` 仅 8 KB，靠 `pkg-config` 找系统库，**不打包源码**，不可用 |

**查证过程留档**：crates.io 上所有纯 Rust 的 RAW 解码器都是 LGPL（`imagepipe` 更是 LGPL-3.0-only），唯一许可宽松的组合是「MIT 绑定 + CDDL 的 LibRaw 本体」。本设计早期版本曾误称 `rawler` 为 MIT/Apache-2.0，已更正。

### 决策二：LibRaw 用 nmake 构建，不用 MSBuild

**理由**：MSBuild 有两个独立障碍，都会同时挡住 CI 与本地构建

1. `buildfiles/libraw.vcxproj` 钉死 **Windows SDK `10.0.18362.0`** 与平台工具集 **`v142`**（VS 2019）
2. 覆盖这两项后仍失败于 `MSB6001`：进程环境块里**同时存在大小写两份代理变量**（`HTTP_PROXY` / `http_proxy`），而 MSBuild 的 `ProcessStartInfo.EnvironmentVariables` 是 .NET 的不区分大小写字典，构造子进程环境时直接抛异常。PowerShell 的 `Env:` 提供程序会把两者规范成一条，从 PowerShell 删不掉

**处置**：`build.rs` 调用 `vcvars64.bat` + `nmake /f Makefile.msvc`。nmake 是纯 Win32 工具，不走 .NET，实测 exit=0。LibRaw 0.22 **没有 CMakeLists.txt**，nmake 是其官方构建路径之一。

**离线**：本变更不引入 crate 依赖，`cargo build --offline` 直接可用；只有 LibRaw 的 C 构建需要本机工具链。

### 决策三：去马赛克交由 LibRaw，不自行实现

**更正**：本设计的早期版本称「去马赛克自行实现」。改用 LibRaw 后此条不再成立，且**自行实现是不必要的风险**——LibRaw 的去马赛克（AHD/DHT/DCB 等）经大量机型验证，自行实现的版本不可能更好。

**理由**：去马赛克质量直接决定后续 ΔE 的上限，伪像与拟合误差会混在一起难以区分。用一个成熟实现把这个变量固定下来，才能让标定环节的误差归因清晰。

**取向**：算法通过 `libraw_set_demosaic` 可配置，并在解码结果中报告实际采用者，使结果可复核。LibRaw 为 CDDL 许可，不污染本仓库。

**边界**：解码层只负责到「线性相机 RGB」为止。**相机 → 工作空间的矩阵由本管线自行施加**，以便掌控色域裁切与负值处理（见决策五）。

### 决策四：管线顺序固定为「解码（含黑电平、白平衡、去马赛克）→ 相机矩阵 → 工作空间 → 基准 → 配方」

**理由**：解码层内部按 dcraw / LibRaw 一脉的既定顺序完成黑电平扣除、白平衡与去马赛克——白平衡在 CFA 上做可避免先插值再缩放带来的色边。工作空间的转换必须早于基准变换，因为基准变换是在**显示参考**下拟合的，顺序颠倒会让拟合结果无法复用。

**要求**：顺序必须确定且可被查询（spec 已写成场景），不允许隐式依赖调用次序。

### 决策五：工作空间取 ProPhoto 线性

**理由**：与 Lightroom Classic / Camera Raw 的内部工作空间一致，使交付环节无需二次转换（这一点在早前的导出规格中已锁定）。

**要求**：中途不裁切色域、不截断负值，色域映射推迟到最终编码。

### 决策六：基准变换表示为「一维色调曲线 + 三维色彩查找表」

**理由**：基准渲染同时包含**非线性色调**与**色彩重映射**两部分，用单一形式表达都别扭——纯矩阵无法表达色调曲线，纯 3D LUT 无法覆盖 HDR 的无限动态范围。拆成两部分后各自可拟合、可单独诊断。

**备选**：只用 3D LUT（动态范围受限）；只用曲线 + 矩阵（色相变化拟合不了）。均已否决。

**约束**：具体规模（曲线采样数、LUT 边长）在实现中由 ΔE 结果决定，不属于 spec 层面。

### 决策七：参考导出必须先按其内嵌 ICC 转换

**理由**：实测 NX Studio 导出的 TIFF 内嵌 `Nikon sRGB 4.0.0.3002`。若当成 sRGB 处理，拟合会把 ICC 的差异吸收进基准变换，产出一个"看起来能过但整体偏色"的结果。

### 决策八：标定数据与渲染代码分离

**理由**：基准变换会随更多参考样本而改进，不应每次重编代码；且 spec 要求多份基准（NEUTRAL、FLEXIBLE COLOR）共存。

## Risks / Trade-offs

- **基准变换可能无法用「曲线 + 3D LUT」拟合到目标精度** → spec 已要求未达标时**明确报告而非静默接受**；若始终不达标，退路是改用直接的三维查找表或增加分段
- **参考导出在 Nikon sRGB 空间，色域受限** → 高饱和区域无法被标定。缓解：优先确认 NX Studio 是否能导出更宽色域的参考（Adobe RGB / ProPhoto）；不能则把标定范围限定在 sRGB 色域内并**在报告中标注该限制**
- **ADL 未关会污染标定** → 参考导出清单把"ADL 关闭"列为前提，校验不通过即排除
- **引入依赖后构建需提权** → 写入 README 与 design；若不接受，退路是回到零依赖但放弃 RAW 解码
- **去马赛克质量直接影响 ΔE** → 拟合误差与去马赛克伪像会混在一起。缓解：先用一张参考样本检查去马赛克本身，再进入拟合
- **参考样本数量少可能导致过拟合** → 拟合集与验证集分开，报告在验证集上的 ΔE

## Open Questions

- **NX Studio 能否导出更宽色域的参考？** 影响高饱和区域能否被标定。可在实现标定工具时先探测，不作为前置阻塞；若不能，按 Nikon sRGB 范围标定并标注。
- **基准变换的具体规模**（曲线采样数、LUT 边长）。可在实现中由 ΔE 与内存占用权衡决定，不改变 spec 的任何场景。
