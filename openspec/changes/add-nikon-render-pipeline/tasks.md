## 3. 色彩管线（capability `render/color-pipeline`）

- [x] 3.1 取得并报告相机 → 输出空间的 3×3 矩阵：矩阵已取出、报告完整 9 分量，并在真实样本上验证。**发现并修正了本任务原先的错误预期**——实测矩阵**不随拍摄白平衡变化**：`DSC_4569` 与 `DSC_5157` 的白平衡系数差异和 0.6152，而矩阵差异和 **0.000000**（逐位相同）。即解码层的相机矩阵按机型标定，**随拍摄条件适配的是白平衡系数**。spec 中对应的场景已改写为「矩阵按机型固定，白平衡系数逐张变化」，并要求两者都被取出与施加。另修掉一个会挡住整个流程的 bug：`libraw_open_file` 收窄字符路径，在 Windows 上按 ANSI 代码页解释，**含中文的路径一个都打不开**（实测 80/80 失败、耗时 0.04 秒）；改用 `libraw_open_wfile` 后正常
- [x] 3.2 自行把该矩阵施加到相机线性 RGB，转入 ProPhoto 线性；已验证恒等矩阵保持数值不变、含负系数的矩阵**产生负分量而不被截断**、超色域值不被裁到 1.0。**并从交叉验证中抓到一处真错误：满量程是 16 位输出的 65535，不是 `color_maximum`（15375）**——后者是原始域白电平；此前按 `1/color_maximum` 归一化会把白电平映射到 4.26
- [x] 3.3 交叉验证：**通过（走路线 B：自行推导矩阵）**。此前残差的根因是 `libraw_get_rgb_cam` 返回的矩阵与输出色彩空间无关、并非实际参与转换的那个（诊断：Camera/sRGB/ProPhoto 三种输出下该矩阵逐位相同，而像素两两平均绝对差 254.7–550.5）。**解法**：用「相机空间像素 ↔ ProPhoto 像素」配对最小二乘把矩阵**测**出来——实测 6,529,215 个样本，rms **0.000005**；在**另一张**照片（`DSC_3307`，6,348,068 样本）上复验，平均绝对差 **0.000007**、最大 0.000025。比此前"施加错矩阵"的 0.008406 好五个数量级。**这同时证明了矩阵按机型固定（3.1 的结论跨图成立），且可以被测量而非复刻解码层内部数据**——因此「矩阵由本管线施加」这条规范得以保留，色域裁切与负值的控制权也保住了。实测推导矩阵为 `[[0.68890,0.32861,-0.01758],[0.01733,1.26110,-0.27849],[-0.01457,-0.10767,1.12218]]`，与 `libraw_get_rgb_cam` 给出的 `[[1.393,-0.216,-0.177],...]` 结构完全不同（两者行和均为 1.0，仅凭行和无法分辨）
- [x] 3.4 实现「不提前裁切色域、不截断负值」：构造含超色域与负值分量的输入，验证各中间阶段保留原值
