## Context

见 `proposal.md` — Why。此处只记录影响实现方式的既有事实，全部为在本机真实文件上的实测结果：

- 配方身份位于 Nikon MakerNote tag `0x0023`，载荷**恒为 108 字节**，实测覆盖 11926 个文件（6248 NEF + 5678 JPG）**无一例外**
- 该载荷前有 8 字节前导头，其中间 u16 取值 `0x01` 或 `0x03`，**与配方身份无关**
- 完整配方不在 NEF 中：字节级搜索显示最长逐字节吻合仅 60 字节
- 配方容器存在两代模板：`0310`（32 个 chunk，978 字节）与 `0300`（22–23 个 chunk，834/904 字节），**曲线块偏移随模板浮动**
- 配对 NEF 与 JPEG 的 108 字节载荷**逐字节完全相同**（可用于交叉校验）
- 本机已有两处配方来源：注册表 4 份、`.nksc` 边车 1 份，其中同一配方存在两代共存的实例

## Goals / Non-Goals

**Goals:**

- 一份解析器同时服务 NEF 与 JPEG，且对两代容器模板都能给出正确结果
- 解析结果对上层足够完整：足以判断"用哪个配方"，并足以取出配方本体
- 解析器对未知字段保持前向兼容，遇到新 tag 不崩溃、不丢数据

**Non-Goals:**

- 不实现渲染、色彩变换、GPU 管线（后续变更）
- 不实现配方文件的**写入**（仅读取；写入待有明确需求再开）
- 不做配方库的持久化缓存与索引文件——本机来源规模很小（个位数到几十份），每次扫描即可

## Decisions

### 决策一：以 IFD 链定位，禁止字节模式匹配

沿 IFD0 → ExifIFD → MakerNote → tag `0x0023` 读取。

**理由**：本次调研中，字节模式匹配连续造成四次误判（把变化的字段当常量、`.search()` 只取首个匹配、JPEG 偏移未加基址、正则写错 magic），每次都表现为"格式不一致"，而数据始终是正确的。IFD 链读取不依赖任何巧合。

**备选**：以 `01 00 ?? 00 02 00 00 00` + `03100310` 的模式匹配定位。已否决。

### 决策二：容器解析按 chunk 遍历，禁止固定偏移

自 `0x10` 起按 `[u32BE tag][u32BE len][payload]` 遍历至 `tag=0 && len=0`。

**理由**：公开的 NP3 布局实现基于 392 字节固定模板，其曲线 LUT 固定在 `0x1CC`。实测本机 `0300` 代文件的曲线块落在 `0xF4` 与 `0x13A`，**按固定偏移会读到错误数据且不报错**——静默产生"看似合理"的错误曲线，是最危险的一类失败。

**备选**：复用公开实现的固定偏移表。已否决（对 `0300` 代失效）；但其**字段语义与编码**（`b−0x80`、`(b−0x80)/4`、8 段混合器顺序）经实测确认可用，予以采纳。

### 决策三：NEF 与 JPEG 共用一套 TIFF 解析，以基址参数区分

**理由**：两者结构相同，唯一差别是 TIFF 头位置——NEF 在文件偏移 0，JPEG 在 APP1 段内 `Exif\0\0` 之后。把基址作为参数传入即可，无需两套实现。这一处正是此前 JPEG 解析全部失败的根因。

**备选**：为 JPEG 单独写解析路径。已否决（重复且易漂移）。

### 决策四：哨兵仅作提示，不构成解析短路

**理由**：曾据调研报告与单个文件断言"哨兵 ⟺ 存在自定义曲线"。全量数据显示哨兵为真恰好等于某一配方的全部文件，但另一份**确含 257 级非恒等曲线**的配方其哨兵却为假——**存在反例**。因此一律按配方名解析配方库，哨兵只上报。

### 决策五：配方等价性以参数判定

**理由**：同一配方在本机同时存在 904 字节（`0300`）与 978 字节（`0310`）两份——NX Studio 保存时会升级重序列化。哈希或长度判等必然误判。

### 决策六：未知 chunk 保留原始载荷

**理由**：`0300` 代缺少公开布局，且规范未定义 `0x0400` 与曲线块内 `BI0\0` 之后的子结构。保留原始载荷使这些字段可在不改动解析器主体的前提下被后续利用。

### 决策七：不引入 ExifTool 源码

**理由**：ExifTool 为 GPL-1.0+/Artistic-1.0 双许可，本仓库为公开仓库。仅采纳其**字段偏移定义**（属事实性接口信息），自行实现解析。

### 决策八：实现语言为 Rust

**理由**：本机 Rust 1.98 + MSVC 已就绪，单一工具链；解析的是逆向得来的二进制格式，边界检查价值高；后续渲染与 GPU 管线（`wgpu`）同栈。

**备选**：C++（LibRaw 原生）。已否决——Windows 上需为每个依赖做 vcpkg/CMake 维护，而本项目在解析层没有任何 C++ 依赖。

## Risks / Trade-offs

- **`0300` 代缺少公开布局** → 以本机 3 个真实样本反推；未知 chunk 保留原始载荷；把"两代均可解析"写成可断言场景而非假设
- **边车 `.nksc` 记录的是 NX Studio 的编辑状态，未必等于拍摄时所用配方** → 以 **NEF 身份为权威**，边车只作为"配方本体"的来源之一；结果中标注来源
- **同名配方多来源可能给出不同参数** → 全部返回并标注来源与代次，由调用方决定，解析层不做静默取舍
- **JPEG 与 NEF 的载荷一致性仅在单对样本上验证** → 任务中包含跨多个文件的批量一致性校验
- **注册表键可能不存在或权限受限** → 来源不可用时正常降级，不使整体失败

## Open Questions

- 容器中 `0x0400` 块与曲线块内 `BI0\0` 之后的子结构语义。可延后：不影响本变更的任何场景，未知块已被保留。
- `0300` 代曲线块内部字段的确切偏移。可延后：本变更只要求"能定位曲线块并取出 257 级 LUT"，具体子偏移在实现时以本机样本确定。
